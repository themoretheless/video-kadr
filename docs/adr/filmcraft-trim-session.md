# Transient Filmcraft trim sessions

Status: native store, authenticated transport and panel integration implemented and qualified by the evidence in docs/filmcraft-parity.md. Decoded playback and full Filmcraft adoption remain open.

Native `DynamicTrimSession` owns the current source document, selected edit points, primary shift counters, exact playhead, initial dynamic snapshot and bounded snapshot history. The browser supplies commands and clocks and renders returned state. It must not calculate frame movement or replay project mutations itself.

The existing stateless document-edit endpoints remain suitable for discrete commands. A live J/K/L sequence needs a server session: every update reapplies its absolute offset to the captured initial document, and commit publishes one document-history change. Sending each intermediate document as a new discrete trim would accumulate clamps and create multiple undo entries.

Create a session from an authenticated user's lossless document, sequence, selected points, linked setting, exact shift and playhead. Return an opaque random session ID and revision zero. Store the authenticated user ID as owner; never trust an owner supplied in the body. Every command resolves the owner again, supplies expected revision and executes serially against that session in the CPU queue. Reject a stale revision without changing the session. A successful command increments revision exactly once, including tick/no-op commands, and returns the current revision.

Expose native shuttle, tick, stop, cancel and play-around commands. IDs, ticks, frame indices and revisions travel as decimal strings. Shuttle direction and speed are finite numbers; clocks and preroll/postroll are finite seconds. Keep public responses typed, with explicit nullable dynamic/around status, the lossless document manifest, counters, playhead and whether a snapshot was committed. The client serializes requests and aborts obsolete work; cancellation of a response alone does not prove a command was cancelled, so it must reconcile revision/state before continuing after an uncertain request.

The session store belongs to `AppState`, not a process-global singleton. Enforce session count and document/snapshot byte limits, expire idle sessions, and provide explicit close. Capacity pressure must refuse a new session or command rather than silently discard an active session. Owner mismatch and missing/expired sessions must not reveal another user's data. Session disappearance must leave the browser's last acknowledged document recoverable. Live clocks, session handles and playback snapshots are transient and do not enter saved project JSON.

For panel integration, capture the pre-dynamic host document once, update preview state without pushing intermediate host history, and push one entry after native commit. Cancel restores the captured document and shift. Play-around changes the exact playhead while leaving project history untouched unless it first commits a dynamic trim. Wire decoded monitor pixels/audio separately; advancing metadata alone is not live playback qualification.

Required evidence: owner isolation, stale/duplicate/out-of-order requests, expiry/close/capacity recovery, finite input validation, original dynamic and play-around corpora through HTTP, one host undo per committed dynamic trim, cancellation/uncertain-response recovery, and browser operation against a running backend. Full engine journal/events/selection cleanup remain separate requirements.

Creation recovery: clients may attach an owner-scoped creationKey (1..128 ASCII letters, digits, underscore or hyphen). The native store retains the key and SHA-256 of the exact serialized creation request for the lifetime of that session. Repeating the same request returns the current acknowledged revision and document without resetting playback or consuming another slot, even at capacity. Changed parameters with the same key return409. Keys are isolated by authenticated owner; expiry/close remove the identity with its session. This is transient process-local recovery, not durable cross-restart idempotency. The panel freezes its original request and holds other edits while a creation response is uncertain; explicit recovery repeats that request without replaying the original shuttle command. Failed teardown cleanup remains bounded by the idle expiry.
