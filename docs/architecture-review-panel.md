7 из 8 запланированных персон (архитектор, разработчик, QA, критик-масштаб,
критик-безопасность, системный дизайнер, UI/UX дизайнер) независимо прочитали
текущий код и дали вердикт. Восьмая (критик корректности/гонок) не смогла
завершить работу - сессия упёрлась в **месячный лимit расходов аккаунта**
(`You've hit your monthly spend limit`), это жёсткий стоп, не транзиентная
ошибка, повторные попытки не помогли и не предпринимались дальше. Всё ниже -
по 7 персонам; корректность/гонки в `jobs/`, `process_control/`, `render/`
специально этим углом не проверялись отдельным критиком (хотя разработчик по
пути нашёл один реальный баг, см. №1 ниже).

**Важно про то, что именно рецензировалось.** Ревизия сделана от последнего
стабильного закоммиченного состояния (`c1400e2` в `main`/`claude/awesome-blackburn-e85742`).
В соседнем ворктри (`~/.codex/worktrees/c86c/video-editor`, тоже `main`) на
момент ревизии шли **живые незакоммиченные правки** другой сессии (вынос
`domain/edit.rs`/`ports/media_export.rs` из `handlers/mod.rs`/`tools/args.rs`) -
туда я не заходил и оценке это не подвергалось, потому что незавершённое
состояние не является надёжной точкой отсчёта.

критик-масштаб, системный дизайнер, UI/UX дизайнер, частично разработчик)
пришли к одному и тому же выводу разными путями, не видя выводов друг друга:

> `bin/perf_corpus.rs`. Реальный `/api/edit` (`handlers/mod.rs`) как строил
> ffmpeg-аргументы напрямую через `tools::build_ffmpeg_args_with_budget`, так

Это ≈2400-3100 строк (архитектор оценил 17% бэкенда, системный дизайнер и UX
дизайнер - независимо похожими числами) production-кода с честными юнит-
тестами, которые **компилируются, тестируются, но физически недостижимы** из
`main.rs -> build_router -> handlers`. Rust не предупреждает о неиспользуемых
`pub`-модулях библиотечного крейта, поэтому `cargo build`/`clippy` этого не
ловят - и, что важнее, ни один прошлый раунд аудита (round 2/3, мой в том
числе) тоже этого не поймал, потому что мы читали код на предмет корректности/
дизайна, а не на predмет reachability.

**Почему это хуже одного god-file** (архитектор): в дереве одновременно живут
два несовместимых пути одной и той же концепции - "EditRequest → ffmpeg args
напрямую" (реальный) и "EditRequest → OutputSpec → EditPlan с fingerprint →
RenderExecution" (spec-путь, никем не используемый). Для внешнего читателя
(и для меня в прошлых раундах аудита) это выглядит как работающая архитектура.

**Практическое следствие для UX** (дизайнер поправляет мою же прошлую
формулировку): диагноз «мощный бэкенд обогнал простой фронтенд» из round 3 -
не совсем точен. Фронтенду физически нечего было «не успеть» отразить у
chunked-рендера/таймлайна/packaging, потому что этой функциональности не
существует за пределами собственных тестов. Реальный, работающий UX-долг
меньше, но реален (см. раздел UX ниже).

## Топ конкретных проблем (после дедупа между персонами)

### 1. 🔴 Баг: `retry_failed` не работает именно для задач, ради которых существует (разработчик)
`backend/src/jobs/store.rs`. Ветка `Failed` в `record_transition` (404-423)
стирает `job_requests.payload_json`, когда `RetryPolicy::default().next_delay`
возвращает `None` - то есть именно когда исчерпаны ретраи или ошибка
неретраибл (`Security`, `Validation`). `retry_failed` (521-528) сам требует
`payload_json <> 'null'` в JOIN - то есть сразу после того, как задача
становится «окончательно неудачной» (и попадает в список Failed для
оператора), кнопка Retry для неё гарантированно вернёт 409 "failed job not
found". `list_failed` не делает такой join и честно показывает задачу -
оператор видит задачу, жмёт Retry, получает непонятную ошибку. Не поймано
тестами: единственный тест `retry_failed` использует `ErrorKind::Timeout` на
attempt 1 (payload не стёрт); тест, который проверяет стирание для
неретраибл-ошибки, не вызывает `retry_failed` после этого, чтобы заметить
поломку.
→ **Решение**: не стирать payload на простом terminal-error, стирать только
при явном discard/succeeded/cancelled; или дать `FailedJob` явный флаг
`payload_available` и обрабатывать его в хендлере до похода в store.

### 2. 🟠 Дублирование retry-планирования в 3-4 местах (разработчик)
`jobs/store.rs`: `retry_failed`, `schedule_retry`, `schedule_due_retries_at` и
кусок `reconcile_started` независимо копируют один и тот же SELECT+apply+
append+persist+outbox-update. Уже разошлись по мелочи (`schedule_due_retries_at`
дополнительно требует `completed_at IS NOT NULL`, остальные - нет).
→ Выделить общий приватный хелпер `schedule_retry_transition`.

### 3. 🟡 Редакция секретов ловит только lowercase-схему URL (критик-безопасность)
`backend/src/privacy.rs`. `next_http_url` ищет буквально `"http://"`/`"https://"` -
`"HTTPS://user:token@host"` полностью обходит редакцию и token/credentials
уходят в **публичное** поле `message` job'ы, отдаваемое клиентом через
`GET /api/jobs/:id`. Единственная реально новая находка по безопасности в
этом раунде (обе прошлые дыры - SSRF-редирект и upload-XSS - подтверждены
закрытыми, с прогонами настоящего `yt-dlp`-бинарника).
→ Регистронезависимый поиск схемы перед вызовом `redact_url`.

### 4. 🟡 Открытый вопрос: наследует ли yt-dlp-как-обёртка-над-ffmpeg прокси (критик-безопасность)
`ytdlp_format()` сам документирует, что для не-HTTP протоколов (часть HLS/DASH)
yt-dlp может делегировать скачивание системному `ffmpeg`, и не гарантированно,
что `--proxy` наследуется так же надёжно, как в нативном пути. Существующий
security-тест проверяет только нативный HTTP(S)-редирект-путь.
→ Отдельный интеграционный тест, форсирующий `--downloader ffmpeg` путь на тот
же приватный sink.

### 5. 🟠 UI для failed jobs (retry/discard) полностью отсутствует, хотя backend готов (UX дизайнер)
`GET /api/jobs/failed`, `GET /api/jobs/registry`, `POST /api/jobs/:id/retry`,
`POST /api/jobs/:id/discard` работают, но `frontend/src/api.ts` их вообще не
вызывает (grep пусто). Пользователь при `interrupted` видит только тост и
должен вручную повторить экспорт с нуля.
→ Панель «Незавершённые операции» с кнопками Повторить/Удалить поверх уже
готовых эндпоинтов - это в основном фронтенд-работа, backend не трогать.

### 6. 🟡 `capabilities.hardware` (VideoToolbox/NVENC/QSV) мертво на обоих концах (UX дизайнер)
Вычисляется в `capabilities.rs`, долетает до `store.ts`, но ни один компонент
его не читает, и ни один `build_ffmpeg_args`-путь не подставляет hardware-
кодек, даже когда он доступен.
→ Либо реально подключить (чип «Аппаратное ускорение» + подстановка кодека),
либо убрать поле из контракта, пока оно ни на что не влияет.

### 7. 🟡 Нет sticky-превью в EditPanel (UX дизайнер, подтверждает мою собственную скриншот-находку из round 3)
`.editor { grid-template-columns: 1.4fr 1fr; align-items: start }` без
`position: sticky` - живое превью (crop/censor overlay, цветокоррекция)
уезжает из вида, пока пользователь долистывает 7 групп контролов вниз к
Звуку/Экспорту.
→ `position: sticky` на левой колонке, либо табы/аккордеон для правой.

### 8. 🟡 Capabilities/health запрашиваются один раз при монтировании, баннер не самовосстанавливается (UX дизайнер)
Типичный сценарий (фронтенд открыт раньше бэкенда, как явно описано в футере
приложения) навсегда оставляет «Сервер недоступен» до ручной перезагрузки.
→ Лёгкий поллинг `loadCapabilities()` пока `backendStatus !== 'online'`.

*(Полный список из 42 находок всех 7 персон, включая low-severity технический

## Расхождение мнений (явно, а не примирено насильно)

**Архитектор** говорит: слои (`http`/`services`/`domain`/`ports`/`jobs`/
`process_control`) в основном спроектированы правильно там, где они реально
используются (`domain/` честно не тянет I/O, `jobs/` транзакционен и
event-sourced по разумной причине) - проблема в **недоведённой интеграции**,
а не в неверном выборе слоёв.

**Системный дизайнер** и **критик-масштаба** говорят жёстче: сами эти слои
(event sourcing + transactional outbox + lease-heartbeat в `jobs/`,
`IsolationTier::Lan/Public` + `SandboxBackend::NsJail/Bubblewrap` в
`process_control/`, `1_000_000`-строчный порог миграции с SQLite) - это
**архитектура для multi-tenant/multi-node сервиса**, которая при этом прямо
противоречит README ("Это MVP: нет аутентификации... Не выставляй наружу как
есть"). По их мнению, даже если бы всё было идеально подключено к HTTP, сама
сложность избыточна для «одного человека на своей машине».

**Обе позиции верны одновременно и не противоречат друг другу**: у
архитектора - оценка *качества исполнения* выбранных абстракций, у системного
дизайнера/критика-масштаба - оценка *правильности самого выбора* строить эти
абстракции для этого продукта. Код может быть одновременно хорошо написан
(loom-верифицированные атомики в `job_cell.rs`, честные транзакции в
`store.rs`, DNS re-validation на каждый connect в `egress_proxy.rs`) и
избыточен для задачи (эти же атомики - ради 1-2 одновременных джобов;
lease-heartbeat - ради единственного процесса, который и так знает о себе
всё в памяти).

**Безопасность** - единственная ось, где панель полностью согласна: обе дыры
прошлого раунда закрыты добросовестно, новая инфраструктура не открыла новой
сетевой поверхности (backup/telemetry/analysis не имеют HTTP-роутов), найдена
одна конкретная новая дыра (redaction case-sensitivity) и один открытый вопрос
(yt-dlp→ffmpeg proxy inheritance).

## Как бы я спроектировал это с нуля (синтез 7 позиций в одну)

Если сводить архитектора, разработчика, тестировщика, обоих критиков,
системного дизайнера и UX дизайнера в одно связное решение - а не просто
перечислять их поимённо - получается так.

**Отправная точка - один явный вопрос перед каждым новым модулем**: «кто
второй потребитель этой абстракции - второй воркер, второй узел, второй
пользователь?» Если ответ «никто, это тот же процесс и тот же человек» -
абстракция не нужна, даже если она сама по себе безупречно SOLID/DRY.
Именно отсутствие этого вопроса на предыдущих раундах ("автономного" роста
за несколько недель) дало 2400+ строк кода, который компилируется, тестируется
и не делает ничего для живого пользователя.

**Jobs**: одна таблица SQLite (`status`/`progress`/`stage`/`started_at`/
`result`/`error`) + `tokio::Semaphore` на `MAX_CONCURRENT_JOBS` в памяти.
Recovery при рестарте - «найти started/queued строки старше N секунд, пометить
interrupted», не event-sourcing с reducer'ом и не lease/heartbeat,
продлевающий аренду у самого себя каждые несколько секунд. Дедуп одинаковых
запросов - один индекс с TTL, не отдельный модуль. Транзакционность самого
`enqueue`/`claim` (то, что реально спасает от потери job при падении процесса
посреди записи) - оставить, это единственная часть, где реально нужна
атомарность на один процесс. `job_cell.rs` - обычный `tokio::Mutex<Job>` вместо
трёх ручных атомиков с loom-верификацией; отмена - через уже существующий в
кодовой базе `CancellationToken`, а не второй самодельный механизм.

**Render**: один `ffmpeg`-процесс на экспорт, как оно физически и происходит
сегодня. Никакого отдельного `EditPlan`/`OutputSpec`/`Fingerprint`-контракта
поверх `tools::build_ffmpeg_args`, пока не появится второй потребитель
(например реальный preview-рендер, отличный от export). Никакого chunked/
resumable encode и per-frame publication - при сбое просто повторить весь
вызов заново (idempotent перезапись temp-файла); если резюмирование
действительно понадобится - сначала измерить частоту сбоев длинных экспортов
через уже существующую `telemetry.rs`, и только имея цифры, решать, оправдан
ли chunking. Multi-clip `Timeline`/`Operation` - явно roadmap-заметка в docs/,
не production-модуль с тестами, пока нет ни одного экрана, где пользователь
может составить таймлайн из нескольких клипов.

**Process isolation**: оставить то, что реально защищает пользователя от его
же (или скачанного) видео и `yt-dlp` - rlimits, process-group kill, allowlist
протоколов, DNS re-validation на каждый connect в egress-прокси (это лучшая
часть всей ревизии - конструктивная защита от TOCTOU, а не разовая проверка).
`IsolationTier::Lan/Public` и `SandboxBackend::NsJail/Bubblewrap` не начинать
писать вообще, пока продукт реально не примет решение стать multi-tenant
сервисом - это отдельный список задач (auth, per-tenant квоты, настоящий
namespace-sandbox), а не то, что дописывается заодно с P0 в тех же раундах
аудита.

**Instrumentation** (`telemetry.rs`, `capabilities.rs` с `schemaVersion`/
`toolFingerprint`, `backup.rs` с content-addressed манифестами): оставить
лишь то, что нужно самому пользователю локально - простой backup/restore без
формального протокола согласования версий, capabilities-эндпоинт без
negotiation (просто «что установлено сейчас»), обычный `RUST_LOG` вместо
выделенной low-cardinality схемы под внешний collector, которого здесь нет и
не планируется, пока продукт не станет сервисом с внешним SRE-наблюдателем.

**Frontend**: домменная логика (`domain/edit.ts`, `domain/geometry.ts` с
phantom types под координатные пространства) - образцовая, её и оставить как
эталон. Визуальный слой - развести на «геометрия и монтаж» (обрезка, кадр,
поворот - привязано к превью через sticky-колонку, требует постоянного
визуального контакта) и «внешний вид и вывод» (цвет, звук, формат - отдельная
вкладка/аккордеон). Зафиксировать 3-4 примитива (segmented-control для
single-select, toggle-chip для тегов, слайдер+число, prominent primary action)
до того, как список полей вырастет ещё - сейчас один `.chip` обслуживает три
разных ментальных модели (взаимоисключающий выбор, теги, разовое действие) под
одним визуальным паттерном. Правило на будущее: **любой PR с новым backend-
контрактом для пользователя (capabilities-поле, retry/discard эндпоинт) обязан
приземлить соответствующий UI в том же PR**, не откладывать фронтенд-часть как
отдельную задачу «на потом» - это и дало текущий разрыв (retry/discard готов на
backend, невидим в UI).

**Правило для будущих раундов аудита** (системный дизайнер): каждый новый
модуль обязан явно указывать, какую строчку из README-раздела «Что умеет» он
обслуживает. Нет строчки - модуль идёт в отдельный `docs/roadmap-future.md`,
не в основной граф зависимостей рядом с реальными хендлерами. Именно
отсутствие такого фильтра дало текущие ~17% недостижимого кода.

## Что не сделано в этом раунде

- Критик №1 (корректность/гонки в `jobs/`/`process_control/`/`render/`) не
  завершил работу - месячный лимит расходов аккаунта. Не перезапускался
  повторно (бессмысленно, пока лимит не поднят/не сброшен).
- Полный список из 42 находок 7 персон не вычитан построчно на предмет
  внутренних дублей между персонами так же тщательно, как в round 3 (там был
  отдельный программный fuzzy-match проход) - здесь дедуп сделан вручную по
  топ-8, длинный хвост может содержать пересечения.
- Ничего из найденного не исправлено в коде - это ревизия/предложение, не
  патч. Одна конкретная правка (retry_failed баг) достаточно локальна, чтобы
  быть сделанной быстро, если понадобится.
